# Plan 4: seats and the metered shared gateway

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An operator turns on a sidekick for an invited person with one command: it creates the seat record,
mints that sidekick's own gateway credential, and writes an invite file. The person's setup page takes the
invite, and from then on every shared-gateway request is metered under the sidekick's pseudonymous client id,
with no message content stored anywhere on the gateway. Removing a seat revokes the credential.

**Architecture:** A new operator command `sksidekick-seat` (same package, never run inside a sidekick) keeps
the seats record (client id to person) in a private per-estate directory, and writes credentials into
skgateway's existing client-auth registry (sha256 of the token only). The invite file carries the gateway URL,
agent id, client id, credential revision and token. In the sidekick, `sksidekick setup --invite FILE` (or the
image's `SKSIDEKICK_INVITE`) stores the seat, and the shared tier writes a named Hermes provider whose
`extra_headers` carry the client-auth headers. A skgateway change makes the verified client id the metering
key and adds a switch that keeps message content out of every log and store.

**Tech Stack:** Python 3.11+ stdlib (`secrets`, `hashlib`, `json`, `os`), pytest; skgateway (Node, its own
test runner) for Task 4; a real skgateway release in CI for Task 5.

**Spec:** sksidekick design, approved 2026-11-20 (private design doc), sections "Seats", "First users",
"Billing and attribution", "Privacy tiers" (shared gateway) and "Calls made by Lumina". Plans 1 to 3
(`docs/plans/`) are the code this builds on. skgateway's client auth (`src/identity/client-auth.mjs`, v1.1.22)
and Hermes' per-provider `extra_headers` (fork at 5727fcb1, `website/docs/user-guide/configuring-models.md`,
"Per-provider request options") are the interfaces it uses.

## Global Constraints

- The gateway learns only a pseudonymous client id. The mapping from client id to person lives only in the
  seats record, on the operator's host, mode 0600 in a 0700 directory. Never in this repo, a log or the gateway.
- Per request the gateway may record only: client id, model, token counts, cost, time (design, "Billing").
- The token is generated once (`secrets.token_urlsafe(32)`), written only to the invite file (0600) and then to
  the sidekick's Hermes `.env`; the registry holds `sha256(token)` hex. No command prints a token.
- Estates stay separate: a seats directory belongs to one estate (`estate` field), and `sksidekick-seat`
  refuses to act when `--estate` or the host's estate (`SKWORLD_ESTATE`) does not match it.
- The registry file format is skgateway's, unchanged: `{"schema_version": 1, "revision": R, "credentials":
  [{agent_id, client_id, token_sha256, credential_revision, revoked, expires_at}]}`, ids matching
  `^[a-z0-9][a-z0-9._:-]{0,127}$`, file mode 0600 owned by the gateway user (or 0640 with its group).
- Client headers, exactly: `Authorization: Bearer <token>`, `x-agent-id`, `x-sk-client-id`,
  `x-sk-credential-revision`.
- Invites must use `https://` unless the gateway host is loopback or a private address (a container next to
  the gateway).
- Nothing phones home: the sidekick talks to the gateway only for model calls the user's tier chose.
- No em or en dashes in any file. Python `>=3.11`; Linux and macOS. This repo is public: no person's name,
  hostname, estate name or internal URL goes into code, tests, docs or commits.
- Out of scope here (each needs the operator's own go): standing up the sidekick gateway instances, giving
  them a public HTTPS name, and delivering invites to the first users.

## Decisions taken for this plan

- **One sidekick gateway per estate, separate from the estate's own gateway.** Turning `client_auth` on for the
  estate gateway would make every estate agent present credentials. A second instance (same release, its own
  port and config) runs with `client_auth.enabled: true` and `privacy.content_logs: false`.
- **`agent_id` is `sidekick` for every seat; `client_id` is `sk-` plus 12 random hex digits.** Nothing about
  the person is derivable from it.
- **Credentials expire after 365 days by default** (`--days`); `sksidekick-seat rotate` issues a new revision
  and a new invite, and revokes the old revision.
- **Remove is revoke plus record.** A sidekick is a standalone island, so the operator cannot export or delete
  it remotely. `remove` revokes the credential, marks the seat removed, and prints the user-side steps
  (`sksidekick export`, then `sksidekick delete`), plus the container commands when the operator hosts it.
- **The invite file is a secret.** It is delivered through the estate's own private file share or vault,
  never pasted into a chat. Setup deletes it after a successful import unless `--keep-invite`.

## Review Focus

1. A seat written for one estate is refused on the other estate's host or directory (estate wall).
2. Two `sksidekick-seat add` runs at once: neither credential is lost (lock around read, modify, write).
3. A revoked or expired invite at setup gives "this invite was turned off or has expired; ask for a new one",
   not "nothing answered".
4. The token never appears in stdout, stderr, the seats record, an export (without `--with-credentials`) or
   the gateway's logs.
5. A sidekick sending another client's `x-app` header is still metered under its own verified client id.
